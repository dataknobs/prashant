From prompts to production-grade agentic systems

Reliable agents are not only a prompt-engineering problem. They are systems, data, security, observability, governance, and operating-model problems that must be engineered as one production stack.

The problem

You built an agent. Now what?

The source deck argues that prompt quality is often not the production bottleneck. Tool behavior, reproducibility, state isolation, prompt injection, and model drift are systems failures.

💥
Tool calls fail silently or repeat non-idempotently

Action systems need contracts, retries, idempotency, and observable failure modes.

🔎
Production failures cannot be reproduced locally

Without full run traces, root-cause analysis becomes slow or impossible.

🧠
The agent forgets context or leaks it across sessions

State and memory require ownership, isolation, retention, and lifecycle rules.

🔒
Prompt injection hijacks behavior

Agent security must protect action boundaries as well as content boundaries.

📉
Model updates silently degrade tuned behavior

Versioned models and eval gates are the change-control layer.

Deck conclusion: these are systems failures, not prompt failures.
Core insight

The unit of quality shifts from prompt to run

Prompt engineering optimizes a single interaction. Agent engineering optimizes a recoverable, observable run that can call tools, maintain state, enforce policy, and survive change.

Prompt engineering

  • Unit of design: a prompt template.
  • Goal: improve a one-shot response.
  • Safety: safe phrasing and refusal behavior.
  • Debugging: manual prompt iteration.
  • Change management: manual tweaks.
  • Security: content boundary only.
→

Agent engineering

  • Unit of design: orchestration graph plus tool contracts.
  • Goal: reliable, recoverable runs at scale.
  • Safety: guardrails, least privilege, and HITL.
  • Debugging: full trace across calls and handoffs.
  • Change management: versioned models and eval gates.
  • Security: content plus action boundaries.
Architecture

The 6-layer production agent stack

The deck organizes a production agent into six layers, ending with a cross-cutting safety and governance plane.

1
Interaction layerUI, API, session and identity management.
2
Orchestration layerRouter, planner, executor, verifier.
3
Tool layerAPIs, MCP servers, code sandbox, RAG and search.
4
State & memory layerSession state and long-term memory treated as a data product.
5
Observability layerDistributed traces, metrics, logs, OpenTelemetry.
6
Safety & governance planeInput, tool and output guardrails; HITL approvals; audit log.
Data-as-product

Agents are data pipelines with reasoning in the middle

Every input, tool output, memory record, and final response becomes a data artifact. The deck argues these artifacts need ownership, schemas, SLAs, retention, validation, and lineage.

Tool outputs

Each tool is a data producer. Version its output schema.

Memory store

Session state is a data product with an owner and retention SLA.

Final outputs

Extractions, summaries, and recommendations are data products.

Audit / lineage

Trace every output to source with run_id and lineage.

Business risk

What breaks without agent engineering discipline

The deck prioritizes four production failure classes: unsafe actions, silent regressions, runaway cost/latency, and failures that cannot be debugged.

SEV-0

Data exfiltration / unsafe action

Prompt injection can cause an agent to ignore policy or act on unauthorized systems, creating real-world and regulatory exposure.

SEV-1

Silent regressions

Model alias changes can degrade tuned behavior without an early warning when eval gates are missing.

SEV-2

Cost & latency runaway

Retry loops can consume 10-100× expected token budgets when circuit breakers are absent.

OPS

Undebuggable production failures

Without full traces, a one-off production failure can take days to root-cause or remain unreproducible.

Deck conclusion: all four are data + systems problems.

Metrics

Measure what actually matters in production

The deck uses four metric families so teams measure outcomes, tools, data products, and security rather than only model-level indicators.

Outcome metrics

  • Task success rate
  • Human acceptance rate
  • Time-to-resolution

Tool quality metrics

  • Tool schema conformance
  • Call accuracy (Ragas)
  • Tool error rate by tool

Data product quality metrics

  • Output schema conformance
  • Data completeness score
  • Grounding / lineage rate

Security / safety metrics

  • Injection ASR (red team)
  • Guardrail tripwire rate
  • Sensitive data leakage rate
Deck position: DataKnobs Kontrols instruments and tracks all four categories out of the box.
