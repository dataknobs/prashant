Agent Deployment

Shipping an agent means releasing a coupled behavior stack: model, prompts, retrieval, memory, tools, permissions, guardrails, and configuration. Production safety depends on moving those layers together and detecting regressions that may never look like a traditional outage.

Overview

Agent deployment ships behavior, not merely code

Traditional software pipelines often ask whether a build succeeded. Agent pipelines have to ask a harder question: did the behavior improve, hold steady, or quietly regress? A deployment can be technically healthy while producing worse answers, taking more expensive tool paths, or drifting from expected policy.

1

Guardrails & policies

Behavioral rules and safety controls move with the release and must be re-tested when the underlying model or tool behavior changes.

2

Tools & permissions

Tool schemas, authorization boundaries, and side effects are part of the deployed product, not infrastructure trivia.

3

Retrieval & embeddings

Retrieval logic and indexes are coupled artifacts. A new embedding model without a matching re-index can silently degrade results.

4

Context & memory

Memory and context configuration shape what the agent knows across turns and therefore change observable behavior.

5

Prompts & instructions

Prompts deserve their own registry and evaluation history because they may change independently of code.

6

Model & parameters

The model is a pinned dependency in many deployments, but changes in version, routing, temperature, or token limits can alter quality, latency, and cost.

The deployment gate must evaluate behavior, not just build health. Same uptime with worse answers is still a failed release.
Lever 1

Use four environments, not three

The deck adds an agent-specific environment between staging and production: shadow. It exposes a candidate version to real production traffic while withholding its output from users, allowing direct behavioral comparison before the first live canary.

DevelopmentMocked tools · fast iteration
StagingProd-like data · full eval suite
ShadowReal traffic · output discarded
ProductionLive users · progressive rollout

What should differ by environment

  • Tools: mocked in development, sandboxed in staging, real in production.
  • Data: synthetic first, then anonymized or production-like, then live with permissions.
  • Blast radius: development can break; production must degrade gracefully.
  • Evaluation: every promotion boundary has a behavioral gate.

Why shadow is different

  • Mirror real production traffic to the candidate.
  • Always return the stable version's response to the user.
  • Compare quality, tool paths, latency, and cost side by side.
  • Run shadow before the first user-visible canary.
Keep the model version pinned consistently across environments unless model change is the thing being tested. Otherwise the staging result may describe a different system.
Lever 2

Containerize the runtime, but version the layers separately

Containers provide the immutable runtime needed for reproducibility, blue-green switching, canaries, and honest rollback. But the deck explicitly separates runtime images from prompts and faster-moving configuration.

Container registry

Runtime artifact

Code, dependencies, and runtime belong in semantic-versioned images that can be redeployed identically.

Prompt registry

Behavior artifact

Prompts are first-class versions with their own change history and rollback path rather than being hidden inside the image.

Config store

Operational artifact

Model choice, temperature, token limits, routing, and tool permissions may need controlled changes without rebuilding the image.

What containers buy

  • Identical runtime across environments.
  • Immutable artifacts that can be redeployed later.
  • Independent scaling and safer component iteration.
  • A clean substrate for canary and blue-green routing.

What not to bake in

  • Secrets and credentials; inject them at runtime.
  • Prompts that should change independently.
  • Configuration that must move faster than image builds.
  • But do pin dependencies that must not drift, such as model versions and tool schemas.
Lever 3

Make behavioral evaluation a blocking CI/CD gate

The evaluation problem

  • Exact-string assertions are often inappropriate for generated output.
  • Score against an eval dataset and a baseline; block regressions.
  • Run the suite for prompt, model, tool, and dependency changes.
  • Add agent-specific security checks for injection, exfiltration, and authorization failures.

Release coupled layers in lockstep

  • A prompt change can require different retrieval behavior.
  • A new embedding model requires re-indexing.
  • Guardrails must be re-tested when the model beneath them changes.
  • Partial release of a coupled stack can create a silent regression even when every service is technically up.
A red eval gate should block the release the same way a failed deterministic test would block ordinary software.
Lever 4

Treat the model as a pinned, swappable deployment dependency

For most teams, the model is consumed through an API rather than deployed as owned infrastructure. The operational discipline remains the same: pin the version, evaluate every change, and have a fallback strategy.

Hosted model API

  • Pin an explicit model version; avoid floating aliases.
  • Treat provider-side changes as changes to your agent behavior.
  • Re-run evaluations on every model change.
  • Plan for deprecation windows and a fallback provider or model.

Self-hosted model

  • You own weights, serving, GPUs, scaling, and uptime.
  • Control and residency can improve because updates are under your authority.
  • The model becomes a true deployable artifact that should be versioned and canaried.
  • Warm-up, batching, and quantization become part of the critical deployment path.
Model routing is also a deployment change. Sending easy work to one model and hard work to another changes quality, cost, and latency together, so route changes should roll out progressively.
Lever 5

Progressive release is the default for uncertain behavior

Because agent behavior cannot be fully predicted in advance, the source recommends a progressive ladder: start with shadow traffic, then expose a small canary cohort, ramp gradually, and reach full traffic only if the metrics remain acceptable.

Shadow0% of users see it
Canary1–5% of traffic
Ramp25% → 50%
Full100%

What the gate watches

  • Error rate and tool-failure rate against the stable version.
  • p95 latency and cost per run, where hidden regressions often appear.
  • Quality scores and user satisfaction, not just uptime.
  • Threshold breaches that can trigger automatic rollback.

Feature flags separate deploy from release

  • Ship code before turning the behavior on.
  • Disable a risky behavior by configuration without an emergency redeploy.
  • Target specific segments and promote by policy.
  • Avoid big-bang release for payments, compliance, and other consequential agents.
Lever 6

Rollback must address both software and side effects

Rolling back code and configuration restores the running system, but it does not erase what the previous agent already did. Emails sent, records written, external tool actions, and memory mutations may need explicit compensating actions.

Blue-green

Keep two live environments and switch traffic back to the stable one.

Feature flag off

Disable the risky behavior through configuration without rebuilding or redeploying.

Pin the prior artifact

Use immutable images so the previous runtime can be redeployed exactly.

Revert the prompt

Roll back the prompt registry independently when code has not changed.

Compensating actions

Undo or remediate the external effects the agent already caused where possible.

Rebuild the index

An embedding rollback is not merely a flag flip; retrieval state may need to be rebuilt.

A rollback path that has never been exercised is only a promise. Rehearse it in staging on a schedule before production pressure makes the first test unavoidable.

Production checklist

What a deployable agent system should be able to prove

Taken together, the deck implies a deployment contract: every behavioral layer is versioned, every promotion boundary evaluates behavior, every risky change has progressive exposure, and every rollback path is tested.

Version inventory

Know the exact runtime image, prompt, model, retrieval/index version, tool schema, and configuration in every release.

Environment parity

Keep the candidate system comparable across staging, shadow, and production so eval results mean what the team thinks they mean.

Behavioral baseline

Score candidates against a stable evaluation dataset and prior production behavior rather than relying on build success.

Progressive exposure

Use shadow, canary, ramp, and feature flags to contain blast radius while metrics are still uncertain.

Rollback rehearsal

Test blue-green switching, artifact rollback, prompt rollback, feature-flag shutdown, and side-effect compensation before emergencies.

Coupled release map

Document which layers must move together, especially embeddings/indexes, guardrails/model versions, and prompts/retrieval behavior.

FAQ

Common questions about agent deployment

Why is agent deployment different from ordinary application deployment?

Because the deployed product is behavior produced by a coupled stack. Uptime can stay healthy while answer quality, tool selection, latency, or cost quietly regress.

What is a shadow environment?

It mirrors real production traffic to the candidate agent while still returning the stable version's response to the user. This lets the team compare behavior on live inputs without user-visible risk.

Why should prompts be versioned separately from containers?

The source treats prompts as first-class behavioral artifacts. Separate versioning allows evaluation and rollback without forcing a runtime rebuild when code has not changed.

When should a model change trigger a full evaluation run?

Every model change should be treated as a behavioral change. The source recommends re-running the evaluation suite even when the model update looks minor.

Why is rollback more than redeploying an old image?

An agent may already have caused side effects: emails, tool calls, records, memory updates, or index changes. The runtime may be reversible while those effects require compensating actions or state rebuilds.
