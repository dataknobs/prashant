Overview

Six decisions shape the system

Agent architecture is not simply a choice of framework. The design starts with six structural decisions: agent count, separation of planning from action, delegation topology, event model, orchestration runtime, and communication protocol.

1

Single vs. Multi-Agent

Choose between one shared reasoning loop and several specialized agents coordinating on a common goal.

2

Planner–Executor

Separate deciding what to do from actually doing it, with the option to re-plan when conditions change.

3

Supervisor–Worker

Use a coordinator to route work to expert workers, validate outputs, retry failures, and aggregate results.

4

Event-Driven Agents

React asynchronously to requests, webhooks, schedules, and other events rather than following a fixed synchronous script.

5

Orchestration Frameworks

Choose the runtime that manages state, memory, routing, handoffs, retries, observability, and human intervention.

6

Communication Protocols

Standardize agent-to-tool communication and cross-agent delegation through open interfaces such as MCP and A2A.

Decision 1

Start with one agent; earn the right to add more

A single-agent design keeps one model, one context, and one reasoning loop around its tools. A multi-agent design splits work across specialists. More agents can increase parallelism and specialization, but they also introduce coordination cost and additional failure modes.

Single-agent strengths

Simple and observable

  • Easier to build, debug, and trace.
  • No synchronization overhead across agents.
  • Lower token cost and usually lower latency.
  • More predictable behavior for bounded workflows.
Watch out

Context can become bloated as tools and task breadth grow, and one loop may struggle with highly parallel or specialized work.

Multi-agent strengths

Specialized and parallel

  • Clear separation of concerns.
  • Independent subtasks can run in parallel.
  • Different roles can use different models or prompts.
  • Scales to broad, heterogeneous problem spaces.
Watch out

Routing, synchronization, retries, tracing, and cross-agent context transfer all become architecture problems.

Rule of thumb: start single-agent. Move to multi-agent only when the work is genuinely parallel, needs distinct expertise, or cannot fit cleanly inside one context.
Decision 2

Planner–executor separates strategy from action

For long tasks, letting an agent jump directly from goal to action can cause drift. Planner–executor architectures introduce an explicit planning phase before execution and allow the system to revise the plan when tool results, failures, or new information invalidate assumptions.

Goal›Planner›Plan›Executor + tools›Result

How the pattern works

The planner decomposes the objective into an ordered task list. The executor runs each step and calls tools as required. Progress is checked against the plan, and failures or new evidence can trigger a re-plan. This deliberately decouples strategic reasoning from operational tool use.

Variants in the source deck

Plan-and-Execute creates the plan first and executes it sequentially. ReWOO plans tool calls up front to reduce model round-trips. LLMCompiler represents work as a task graph so independent steps can run in parallel.

Decision 3

Supervisor–worker creates a clear control hierarchy

A supervisor owns the overall goal, delegates subtasks to specialized workers, validates results, and aggregates the final answer. It is a natural pattern when multiple roles are useful but the system still needs one point of accountability.

Strengths
  • Clear control and accountability.
  • Workers can remain narrow and expert.
  • Workers are easy to add, replace, or nest.
  • The supervisor can route, retry, and validate.
Failure modes
  • The supervisor can become a bottleneck.
  • It can become a single point of failure.
  • Poor routing quality caps overall system quality.
  • Too much context can accumulate at the top.

Hierarchies can also be recursive: a worker can itself become a supervisor for a smaller sub-team. That makes the pattern extensible, but each additional layer increases observability and coordination requirements.

Decision 4

Event-driven agents fit asynchronous and long-running work

An event-driven system replaces a fixed request-response script with publish/subscribe behavior. Requests, API webhooks, schedules, and timers generate events; independent agents subscribe and react asynchronously.

Why it changes the architecture

Event-driven designs loosen coupling between components. Producers do not need to know exactly which agent will consume an event, and new subscribers can be introduced without changing the producer. This makes horizontal scaling and parallel handling easier.

Best-fit workloads

  • Real-time alerts, monitoring, support, and reactive systems.
  • Long-running or human-in-the-loop workflows that wait on external events.
  • High-throughput pipelines with parallel, independent handlers.
The trade-off is operational: distributed event flow is harder to trace, ordering and eventual consistency must be designed intentionally, and retry/dead-letter handling becomes essential.
Decision 5

Orchestration frameworks operationalize the design

The framework is the runtime layer that turns the chosen architecture into a managed system. The deck groups orchestration into four styles: graph-based, role-based, handoff-based, and hierarchical.

Decision 6

Protocols separate vertical tool access from horizontal agent collaboration

The deck frames agent communication in two directions: down to tools, data, and APIs, and across to other agents. Open protocols aim to standardize those boundaries.

MCPModel Context Protocol

Vertical connectivity between an agent and tools, data, or APIs using a client-server interface.

A2AAgent-to-Agent

Horizontal communication for discovery, authentication, and delegation across agents and stacks.

ACPAgent Communication Protocol

A lightweight, REST-oriented approach to agent messaging, described in the deck as converging toward the A2A direction.

ANPAgent Network Protocol

An emerging decentralized-identity approach aimed at open agent networks and marketplaces.

Design principles

What to optimize for in production

Across all six decisions, the architecture should minimize unnecessary coordination while making state, control, recovery, and accountability explicit.

Minimize moving parts

Use the smallest architecture that can meet the workload. Extra agents are not free abstractions.

Make control visible

Know who owns the goal, who can delegate, and where the execution state lives.

Design failure paths

Retries, re-planning, dead-letter handling, validation, and escalation should be architectural concerns.

Keep boundaries explicit

Differentiate tool invocation, agent handoff, asynchronous events, and shared state.

Instrument the runtime

Multi-step and multi-agent systems need tracing to reconstruct what happened and why.

Scale by need

Add parallelism, specialization, and hierarchy only when the workload justifies them.

FAQ

Common architecture questions

Should every complex AI workflow use multiple agents?

No. The source deck explicitly recommends starting with a single agent and moving to multiple agents only when work is genuinely parallel, requires distinct expertise, or exceeds what one context can manage cleanly.

When is planner–executor useful?

It is useful for long, multi-step tasks where direct action tends to drift. The re-plan loop is important when failures or new information can invalidate the original plan.

What is the main risk of supervisor–worker systems?

The supervisor can become both a bottleneck and a single point of failure, and the quality of its routing decisions constrains the quality of the overall system.

Why use event-driven agents?

They suit reactive, asynchronous, long-running, or high-throughput workloads where agents should respond to events independently rather than block in a fixed script.

What does an orchestration framework provide?

The deck highlights state and memory, control flow and routing, handoffs, retries and error recovery, tracing and observability, and human-in-the-loop support.

How do MCP and A2A differ in this model?

MCP is presented as the vertical interface between agents and tools/data, while A2A is the horizontal interface for communication and delegation between agents.
