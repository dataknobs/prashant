The Observability Gap in Agentic Systems

Read slide 2 text
The Observability Gap in Agentic Systems 2 / 8 naive_agent.py # A typical agent loop looks healthy from the outside... def run_agent(task): plan = llm.plan(task) # one opaque call for step in plan.steps: result = execute(step) # tool call, no record if result.failed: retry(step) # silent retry return plan.final_answer # All your APM dashboard shows: # POST /agent/run 200 OK 4.8s # # What happened inside those 4.8 seconds? # - 3 LLM calls, 2 tool calls, 1 silent retry # - which step burned the most tokens? # - which tool call actually failed, and why? # Request/response tracing can't answer any of it. ! Why agents break conventional monitoring • Multi-step, dynamic call graphs no two runs trace the same path • Cost and latency vary per run, not just per endpoint • Failures surface mid-plan, not at the API boundary • “Success” itself is fuzzy outputs are non-deterministic

Structured Tracing: A Span for Every Step

Read slide 3 text
Structured Tracing: A Span for Every Step 3 / 8 tracer.py import time, uuid, json class Span: def __init__(self, name, parent=None, **attrs): self.id = uuid.uuid4().hex[:8] self.name, self.attrs = name, attrs self.parent = parent.id if parent else None self.trace_id = (parent.trace_id if parent else uuid.uuid4().hex) self.start = time.time() def __enter__(self): return self def __exit__(self, *exc): ms = (time.time() - self.start) * 1000 emit(self.trace_id, self.id, self.parent, self.name, ms, self.attrs) with Span('agent.run', task_id='t-882') as run: with Span('llm.plan', run, model='gpt-5'): steps = call_llm(task) for step in steps: with Span('tool.call', run, tool=step.name): execute(step) { } What good tracing captures • Parent/child spans so you can rebuild the whole run as a tree • Per-step attributes: model, tokens, tool name, latency • A trace_id that threads across LLM calls, tools, and sub-agents • Enough detail to replay exactly what the agent decided, and why

Core Metrics: Latency, Cost & Tool Success

Read slide 4 text
Core Metrics: Latency, Cost & Tool Success 4 / 8 metrics.js // metrics.js lightweight in-process collector class Metrics { constructor() { this.samples = []; } record(step, { ms, tokens, tool, ok }) { this.samples.push({ step, ms, tokens, tool, ok }); } percentile(p) { const s = this.samples.map(x => x.ms).sort((a, b) => a - b); return s[Math.floor((p / 100) * (s.length - 1))]; } toolSuccessRate(tool) { const runs = this.samples.filter(x => x.tool === tool); return runs.filter(x => x.ok).length / runs.length; } costPerRun(pricePer1k = 0.01) { const tok = this.samples.reduce((n, x) => n + (x.tokens||0), 0); return (tok / 1000) * pricePer1k; } } // m.percentile(95) -> p95 step latency, in ms # Metrics worth dashboarding • Step latency at p50 / p95 / p99 not just overall run time • Cost per run and per session, broken out by model and tool • Tool-call success rate and retry rate, per tool • Step-count distribution a proxy for plan complexity creeping up

LLM-as-Judge: Scoring Outputs at Scale

Read slide 5 text
LLM-as-Judge: Scoring Outputs at Scale 5 / 8 judge.py JUDGE_PROMPT = '''Rate the answer 1-5 on: faithfulness (matches the retrieved facts) and completeness (covers every part of the task). Return JSON: {"faithfulness": n, "completeness": n, "reason": "one sentence"}''' def judge(task, answer, context, model='gpt-5'): reply = call_llm( model=model, system=JUDGE_PROMPT, temperature=0, user=f'Task: {task}\nContext: {context}\n' f'Answer: {answer}', ) score = json.loads(reply) score['passed'] = (score['faithfulness'] >= 4 and score['completeness'] >= 4) return score # run across a batch, never one example at a time results = [judge(r.task, r.answer, r.context) for r in batch] pass_rate = sum(r['passed'] for r in results) / len(results) ✓ Making LLM judges trustworthy • Score against a written rubric, not a vague “is this good?” • Force structured JSON output so scores are machine-checkable • Run judges at temperature 0 and sample-check against humans • Use two judges and flag disagreement, rather than averaging it away

Golden Datasets & Regression Testing

Read slide 6 text
Golden Datasets & Regression Testing 6 / 8 eval_gate.py # eval_gate.py runs in CI before every deploy golden = load_dataset('golden_set_v7.jsonl') baseline = load_scores('baseline_scores.json') current = [judge(ex.task, run_agent(ex.task), ex.context) for ex in golden] current_rate = sum(r['passed'] for r in current) / len(current) baseline_rate = baseline['pass_rate'] regression = current_rate < baseline_rate - 0.02 # 2-pt tolerance print(f'pass_rate: {current_rate:.2%} (baseline {baseline_rate:.2%})') if regression: print('REGRESSION DETECTED blocking deploy') sys.exit(1) save_scores('baseline_scores.json', {'pass_rate': current_rate}) ✓ Running evals like tests • Curate a golden set from real traffic plus known edge cases • Version the golden set scores mean nothing against a moving target • Gate deploys on a regression threshold, not one eyeballed run • Re-baseline deliberately after an intentional behavior change

Anomaly Detection & Alerting on Agent Drift

Read slide 7 text
Anomaly Detection & Alerting on Agent Drift 7 / 8 drift_monitor.js // drift_monitor.js rolling z-score on a live metric stream const window = []; const WINDOW_SIZE = 50, Z_THRESHOLD = 3; function check(value) { window.push(value); if (window.length > WINDOW_SIZE) window.shift(); const mean = window.reduce((a, b) => a + b, 0) / window.length; const variance = window.reduce( (a, b) => a + (b - mean) ** 2, 0) / window.length; const z = (value - mean) / (Math.sqrt(variance) || 1); if (Math.abs(z) > Z_THRESHOLD) { alert(`tool_failure_rate drifted: z=${z.toFixed(2)}`, { value, mean }); } return z; } // stream.on('tool_failure_rate', check) ▲ Alerting without alert fatigue • Alert on statistical drift, not static thresholds that go stale • Watch error rate, cost, and latency together not one in isolation • Page on sustained drift, not a single noisy spike • Route alerts to the owning agent/team, not one shared firehose
