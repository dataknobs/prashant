By Prashant Dhingra · DataKnobs · Updated November 17, 2026 · Part of Generative AI 101

Retrieval-augmented generation (RAG) is the most widely used way to make a language model useful on private, current information. Instead of hoping the model memorized the answer, you retrieve the relevant passages first and give them to the model with the question. This guide walks through each stage of a production pipeline, how vector databases make retrieval fast, the advanced patterns teams use now, and how to measure whether it all works.

Key takeaways

  • Retrieval quality caps answer quality. Most RAG failures are search failures, not model failures.
  • Hybrid search plus re-ranking (vectors for meaning, keywords for exact terms) is the reliable default.
  • Chunk with structure in mind, and keep metadata such as source, date and permissions with every chunk.
  • Measure retrieval and generation separately: context precision and recall, then faithfulness and answer relevance.

Why RAG, and when to use it

A model's built-in knowledge is frozen at training time, generic, and impossible to audit. RAG fixes all three. You update knowledge by changing documents rather than retraining, you control exactly what the model can see (including per-user permissions), and every answer can cite its sources.

Use RAG when answers depend on domain-specific, fast-changing or private information: policies, product catalogs, contracts, research, tickets, regulations. It's also the most direct defense against hallucination, because the model is asked to answer from evidence it was given and to say so when the evidence is missing.

The RAG pipeline, stage by stage

Retrieval-augmented generation tutorial: adding knowledge to an LLMRAG overview: retrieve relevant context before generating an answerRAG architecture: ingestion, embeddings, vector index, retrieval and generation
  1. Ingest and parsePull content from file shares, wikis, databases and apps. Parse PDFs, tables and slides carefully: layout errors here poison everything downstream. Capture metadata such as source, owner, date and access rights.
  2. ChunkSplit documents into passages small enough to be precise but large enough to stand alone. See the chunking table below.
  3. EmbedConvert each chunk into a vector with an embedding model. Use the same model for documents and queries, and re-embed everything if you change models.
  4. IndexStore vectors in a vector index and, ideally, the text in a keyword (BM25) index too, with metadata for filtering.
  5. RetrieveFor each question, run hybrid search (vector plus keyword), apply metadata and permission filters, and take the top 20–50 candidates.
  6. Re-rankScore candidates against the question with a cross-encoder or LLM re-ranker and keep the best handful. This step often gives the largest single quality gain.
  7. Generate with citationsPut the passages in the prompt with source labels, instruct the model to answer only from them, cite each claim, and say when the answer isn't present.
  8. Evaluate and monitorTrack retrieval and answer metrics on a fixed test set and on live traffic, and log which sources were used for every answer.

Measuring the stages separately tells you where to fix things. Low recall means work on parsing, chunking or search; high recall with low faithfulness means work on the prompt or the model.

Advanced RAG patterns

  • Query rewriting: turn a vague or conversational question into one or more precise search queries before retrieving.
  • Agentic RAG: the model decides whether to search, what to search for and when it has enough, across several rounds. It's now built into major platforms, for example the agentic retrieval in Amazon Bedrock's managed knowledge base and in Microsoft Foundry IQ.
  • GraphRAG: extract entities and relationships into a knowledge graph, then retrieve connected facts. It's strong for "how is X related to Y" questions across many documents.
  • Multi-hop retrieval: answer in steps, using what one search found to drive the next.
  • Structured plus unstructured: route numeric questions to SQL or an API, and narrative questions to document search, then combine the results.

How vector databases work

Vector database: storing and searching high-dimensional embeddingsVector database use cases: semantic search, Q&A bots, recommendations and image searchVector database vs traditional database: similarity search vs exact match

A vector database stores embeddings and finds the ones closest in meaning to a query vector. Comparing a query against millions of vectors exactly would be slow, so these systems use approximate nearest-neighbor (ANN) indexes that trade a little accuracy for very large speed-ups:

  • HNSW (hierarchical navigable small-world graphs): fast and accurate, memory-hungry. It's the most common default.
  • IVF (inverted file): clusters vectors and searches only the nearest clusters.
  • Product quantization: compresses vectors to cut memory, at some cost in accuracy.

Traditional databases excel at exact matches over rows and columns. Vector databases excel at "find things like this": semantic search, Q&A bots, recommendations, similar images or designs, and anomaly detection.

They combine well. A fine-tuned model can still use RAG, and RAG can feed a long-context model a focused set of documents rather than everything.

Common failure modes and fixes

  • Right document, wrong chunk: use structure-aware or parent–child chunking.
  • Exact terms missed (product codes, names): add keyword search alongside vectors.
  • Stale or duplicate content: deduplicate at ingestion and prefer newer sources using date metadata.
  • Permission leaks: filter on access metadata at retrieval time, never just in the prompt.
  • Confident answers without evidence: require citations and allow "not found".
  • Poisoned or injected documents: treat retrieved text as untrusted data, not instructions.

RAG and vector databases: frequently asked questions

What is retrieval-augmented generation?

Retrieval-augmented generation (RAG) is a technique in which relevant passages are retrieved from a knowledge base and supplied to a language model along with the question, so the answer is grounded in current, citable sources rather than the model's memory alone.

Do I need a vector database for RAG?

Not always. Small collections can use a vector extension such as pgvector, a search engine with vector support, or a cloud-managed knowledge base. A dedicated vector database makes sense at larger scale or when you need advanced filtering and performance.

What is hybrid search?

Hybrid search combines vector (semantic) search with keyword search such as BM25, then merges the results. It finds passages that match the meaning of a question and also those containing exact terms like product codes or names.

Is RAG better than fine-tuning?

They solve different problems. RAG supplies current, private, citable knowledge; fine-tuning changes behavior such as format, tone or a narrow skill. Many production systems use RAG first and add fine-tuning only if needed.
